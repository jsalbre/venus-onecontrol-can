## Unreleased

- 2026-08-25: README.md's Installation section still showed the tarball built and staged through bare `/tmp` on both ends -- stale against the actual staging convention (`dist/` locally, `/data/venus-onecontrol-can.tar.gz` on the Cerbo, matching where the project itself lives). Also added `--no-xattrs --no-acls --no-fflags` to the example `tar` command -- without them, macOS's bsdtar embeds Apple xattr/PAX headers that Linux `tar` warns about (harmlessly, but noisily) on extraction.
- 2026-08-25: `routing.py`'s `route_device_id()` now checks `already_created` before `is_exposed()`, not after -- for a device whose D-Bus service already exists, this skips the config read/scan entirely instead of doing it and discarding the result. Also fixes a real, if minor, side effect of the old order: a device un-exposed after its service was created would re-log to `discovered_devices.json` on every subsequent DEVICE_ID broadcast (since it'd hit `NOT_EXPOSED` instead of `ALREADY_CREATED`); now it doesn't. Confirmed no test depended on the old order (only test exercising `already_created=True` also has `expose=True`), and nothing in `publisher.py` removes an existing service on un-expose either way, so this has no effect on the D-Bus service itself. `find_device()`'s linear scan (the other flagged contributor) was left alone -- still microseconds-scale at <=31 devices, not worth the added complexity of a separately-invalidated index for no measurable gain. 320 tests passing.
- 2026-08-25: Confirmed the PID 161 live-read on real hardware: a real dimmer (PID 161=0) still shows with a working Dimming path, and a device configured as latching (PID 161=1) now shows as a plain on/off light in the Venus OS GUI instead of always rendering as a dimmer. Closes out the last open item for this feature.
- 2026-08-25: The PID 161 live-read flow (`publisher.py`) was silent on its two normal paths -- no log line when the read was requested, none when it resolved successfully; only the timeout/failure branch logged, and at DEBUG, which is backwards for a case that means the read didn't work as intended. Fixed: the request and the resolved-successfully outcome now log at INFO (`"...requesting PID 161 (SIMULATE_ON_OFF_STYLE_LIGHT) read"`, `"...PID 161 read resolved, dimming_capable=%s"`), and the timeout case is now WARNING instead of DEBUG.

- 2026-08-24: `publisher.py` now reads PID 161 (`SIMULATE_ON_OFF_STYLE_LIGHT`) live so a `dimmable_light` configured to behave as a plain on/off switch displays as an on/off light in the Venus OS GUI instead of always rendering as a dimmer. First-ever active (non-passive) CAN request from `publisher.py` -- everything before this was either broadcast decoding or command-sequencer traffic. Reads never need a session (unlike writes, which need `DIAGNOSTIC`), but `publisher.py`'s GLib main loop is fully event-driven and can never block waiting for a response, so this follows the same async request/response pattern already established for commands (`CommandAttempt`), just simpler -- one step, not three. New `_PendingDimmableRead`/`_pending_dimmable_reads` (mirrors `_pending_commands`'s shape), a new `_handle_dimmable_pid_read_response()` dispatch in `_handle_extended_frame()` (disambiguated from command responses by request code), and a 500ms timeout sweep (2.0s timeout, falls back to today's dimmer-assumed behavior on failure/timeout/unsupported PID). Design choice: a `dimmable_light`'s D-Bus service creation is now delayed until the read resolves, rather than created immediately and mutated afterward -- `SwitchService`'s `Settings/Type`/`Dimming` path are fixed at construction with no existing mechanism to change them later, and delaying creation (up to ~2s, once, at creation only) was judged simpler and lower-risk than building that mechanism. `device_class` itself is deliberately left unchanged ("dimmable_light" either way) since the underlying CAN command shape doesn't depend on PID 161, only the device's physical response does -- added a `dimming_capable` parameter instead, threaded through `SwitchService`/`device_mapping.output_type_for()`. Added a proper `PID_SIMULATE_ON_OFF_STYLE_LIGHT = 161` constant to `pid_client.py` (previously only an inline literal). Not yet run on real hardware -- the async machinery in `publisher.py` has no unit test coverage (consistent with the rest of its dbus/gi-dependent code), though `output_type_for()`'s new parameter does. 320 tests passing.

- 2026-08-24: Fixed the real root cause of `publisher.py` using 11-12% CPU on real hardware (vs. 3-4% for the next-heaviest process, per `top`/`htop`) -- investigated by tracing every call on the hot path directly against the real code. Root cause: `ConfigManager` had zero in-memory caching -- every read (`is_exposed()`/`find_device()`/`get_devices()`/etc.) did a full file-open + exclusive `flock` + `json.load()` + O(n) scan on every call, and `routing.route_device_id()` calls `is_exposed()` on every DEVICE_ID broadcast before its `already_created` short-circuit, so even a device whose service was created hours earlier re-triggered a full disk read on every ~1-3Hz re-broadcast -- 20-90+ full read cycles/sec, sustained, on this coach's 20-31-device bus. Added an in-memory cache keyed on `(inode, mtime_ns, size)` from a single `stat()` call, with `st_ino` as the load-bearing signal since `_atomic_write()` always replaces the file via tempfile+`os.replace()` (inode changes on every write, regardless of filesystem mtime resolution) -- this must, and does, still detect an external process (`manage-devices`/`manage-system`) editing `config.json` while `publisher.py` keeps running, preserving the live-reconfiguration property confirmed earlier. `DiscoveryLog` (`discovered_devices.json`) got the identical caching treatment, plus a real adjacent bug fix found along the way: its writes weren't atomic and it had no locking despite being written from two processes (`publisher.py`'s `record()` and `manage-devices`' `prune_configured()`) -- both classes now share one `_atomic_write_json()` helper. Three smaller fixes rode along: `tank_service.py`/`motor_status_service.py`'s `update()` methods now batch their D-Bus property writes into one `ItemsChanged` signal (`with self._dbusservice as s:`, matching `switch_service.py`'s existing pattern) instead of one `PropertiesChanged` per changed path -- highest-value for motor devices, which broadcast at ~333ms while moving and previously fired up to 6 separate signals per update; `publisher.py`'s `self.services`/`self._pending_commands`/`self._queued_commands` are now keyed directly by the already-hashable `StableKey` dataclass instead of a rebuilt `.to_config_string()` on the two hottest per-frame lookups; `_finalize_command_attempt()`'s signature simplified to derive its key from `CommandAttempt.key` instead of threading a redundant separate parameter through both callers. 5 new tests added (`tests/test_config_manager.py`) including the concrete regression test for the must-not-regress property (an independent second `ConfigManager` instance simulating an external process write, asserting the first instance's next read reflects it) -- caught one real bug of its own along the way: the first cache-snapshot implementation only copied the outer `devices` list, not each individual device dict, so a caller mutating a returned device dict could still corrupt the cache. 317 tests passing. Deliberately deferred (flagged, not fixed): `routing.py`'s exposure-check-before-already-created ordering still costs one now-cheap O(n) scan per frame for already-created devices, and `find_device()`'s O(n) linear scan is unindexed -- both microseconds-scale at ≤31 devices, not worth touching a "fails closed at every step" safety module for. Not yet deployed/measured on real hardware. See `ARCHITECTURE.md`'s "Config-Gated D-Bus Exposure" design decision.
