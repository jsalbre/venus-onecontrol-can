## Unreleased

- 2026-08-21: Confirmed on real hardware that a `commands_enabled: false` device transmits nothing on a write attempt. Toggled a device configured `expose: true` / `commands_enabled: false` repeatedly in the Cerbo GUI while running `candump_logger.py` in parallel -- the service log showed the expected `COMMANDS_NOT_ENABLED` refusal each time, and decoding the parallel capture with `candump_replay.py` found zero `COMMAND` frames and no bridge-originated `REQUEST` traffic in the window. See TODO.md's Phase 3 checklist for the one remaining rollout item (a real power-loss test).
- 2026-08-21: Built and confirmed the PID write path, fixing the Kitchen Island Light dimming problem end-to-end on real hardware. `can_link/session.py`'s `SessionClient`/`tea_transform()` were generalized to an arbitrary SESSION_ID/cypher (previously hardcoded to REMOTE_CONTROL) -- backward-compatible, all existing REMOTE_CONTROL behavior and real-hardware fixtures unchanged. `can_link/pid_client.py` gained `build_pid_write_request()` (same 0x11 request code as a read, distinguished by payload length). Shared bus/address-claim/request-response plumbing was extracted from `pid_probe.py` into a new `src/tools/probe_common.py` once a second tool needed it. New `src/tools/pid_write.py`: a deliberately separate, `--confirm`-gated CLI (never wired into `manage-devices` or `publisher.py`) that opens a DIAGNOSTIC session, writes one PID, and verifies via a read-back rather than trusting the write reply's own previously-unconfirmed shape. First real write attempt against Kitchen Island Light (PID 161, 1-byte value matching a read's width) was rejected `RESPONSE.BAD_REQUEST` -- the DIAGNOSTIC handshake itself worked (first real validation of any session type besides REMOTE_CONTROL), so the rejection meant the payload shape was wrong, not the session. Retrying with the PID's full declared `UINT48` (6-byte) width succeeded: `RESPONSE.SUCCESS`, confirmed by read-back. The user then confirmed the fix physically -- Kitchen Island Light dims correctly now, and the OneControl phone app shows it as a dimmer too after a restart. This also confirmed the write success-reply shape (matches a normal read reply exactly) and a write error-reply shape for `BAD_REQUEST` (a single raw byte, shorter than a read error's confirmed 5-byte shape). 306 tests passing. See `ARCHITECTURE.md`'s "PID Reconfiguration" design decision and `dev-notes/ARCHITECTURE.md`'s new "PID Writes -- Confirmed Real" section.
- 2026-08-21: Found the real root cause of the Kitchen Island Light dimming problem. `--list-pids` (added just prior) run against both Kitchen Island Light (misbehaving) and Kitchen Pendants Light (working) returned an identical 97-PID supported set on both, with identical flags -- ruling out "one device supports a config PID the other doesn't" and narrowing it to a value difference within that shared set. Fetched the full named PID catalog from the decompiled source (`assembly_0080_Sharp.decompiled.cs`, 449 `new PID(<num>, "<NAME>", ...)` entries) and cross-referenced all 97 discovered PID numbers against it, surfacing `PID 161 = SIMULATE_ON_OFF_STYLE_LIGHT` (DIAGNOSTIC-gated, writable) -- a name matching the user's own description of the problem almost exactly. Reading PID 161 against both real lights confirmed it directly: `1` (true) on Kitchen Island Light, `0` (false) on Kitchen Pendants Light -- the only difference between the two devices anywhere in the 97-PID set. This also incidentally resolved a standing open question: `pid_client.py::parse_pid_reply()`'s success-reply shape (unvalidated since 2026-08-19, no PID_READ_WRITE traffic had ever been captured) turned out to be correct as originally implemented -- the real PID 161 reply (`00 A1 01`) decodes exactly as already coded, no change needed. Write path (DIAGNOSTIC session, PID-write builder, actually flipping PID 161 to `0`) is a separate, not-yet-started planning pass. See `ARCHITECTURE.md` and `dev-notes/ARCHITECTURE.md`.
- 2026-08-21: Cross-check run (Fresh Tank, with its independently-known and different real `DeviceType`) confirmed the previous finding rather than reopening it: PID 183 (`DEVICE_TYPE`) and PID 451 (`LOAD_TYPE`) returned byte-identical replies across a tank sensor and two dimmable lights. Decoded the reply's trailing byte against the decompiled `enum RESPONSE : byte` (a plain sequential C# enum, cross-checked and matching every previously-known named value) -- it's `UNKNOWN_ID` (4) in every case, meaning neither PID is recognized on this Unity X270 hardware family at all, not a byte-layout bug. This also gave a confirmed, real error-reply format for both `PID_READ_WRITE` and `PID_GET_PROPERTIES` (`can_link/pid_client.py::RESPONSE_CODE_NAMES`), used to make `pid_probe.py`'s diagnostic output name the actual error instead of just flagging a mismatch. Guessing further PID numbers from a catalog that may not even apply to this hardware isn't productive, so added `PID_READ_LIST` (request code `0x10`) support instead -- `pid_client.build_pid_list_request()`/`parse_pid_list_reply()` and `pid_probe.py --list-pids`, confirmed against the decompiled server handler (`Request10PidReadList`): enumerates every PID a specific real device actually supports, paginated, so the next step is discovery instead of another guess. Still read-only, no session, cannot change device configuration. 295 tests passing.
- 2026-08-21: First real `pid_probe.py` run (against the Kitchen Island and Kitchen Pendants dimmable lights) surfaced a real bug in the probe tool itself (it printed the *requested* PID, not the one actually echoed in the reply -- fixed, now always shows raw hex and flags a mismatch explicitly) and, more significantly, real evidence that this project's documented `PID_READ_WRITE` reply byte layout (never actually validated against a real capture before now) is likely wrong -- the real reply doesn't echo the requested PID at the documented offset, but does at a 2-byte offset, and even accounting for that the resulting value contradicts each light's already-confirmed real `DEVICE_TYPE` from its `DEVICE_ID` broadcast. Not fixing `pid_client.py`'s parser yet -- two data points isn't enough to safely change code every PID read depends on; next step is a cross-check against a device with an independently-known, different `DeviceType` (a tank sensor) before drawing conclusions. See `dev-notes/ARCHITECTURE.md`'s `PID_READ_WRITE` section.
- 2026-08-21: Researched device reconfiguration (assigning a name to an unused Unity X270 input/output, and a real problem -- one of the X270's 4 dimming-capable outputs, driving the Kitchen Island lights, behaves as a plain on/off latch in both the OneControl app and this project despite dimmable-capable hardware) against decompiled LippertConnect source and Lippert's own official `OneControl Configurator Guide` (CCD-0001830). Confirmed PID writes reuse the existing read request code (`0x11`, distinguished by payload length); confirmed the rename/reassign mechanism (PID 4/5) is real and documented, but corrected an earlier, never-implemented guess in this project's own notes -- it requires the DIAGNOSTIC session (SESSION_ID=2), not REMOTE_CONTROL (SESSION_ID=4), cross-validated numerically against the already-proven REMOTE_CONTROL constant. Found that the dimmable-output problem doesn't match any documented Lippert feature the way it was first described (no dimmable-to-relay conversion exists in their own tooling); `LOAD_TYPE` (PID 451) is a real but unconfirmed candidate for what's actually clamping it. Since no real validating capture is possible here (confirmed with the user -- only the physical touchscreen can reconfigure a device, and this installation doesn't have one), built a read-only diagnostic probe instead of guessing at a write-path design: `can_link/pid_client.py` gained `PID_GET_PROPERTIES` (request code `0x12`) support, and a new `src/tools/pid_probe.py` CLI queries real PID values and writability against an actual device -- no session, no writes, cannot change anything. 288 tests passing. See `ARCHITECTURE.md`'s "PID Reconfiguration" design decision and `dev-notes/ARCHITECTURE.md`'s new SESSION_ID/PID_GET_PROPERTIES protocol reference for the full research. The actual write path is deliberately deferred until this tool returns real evidence.
- 2026-08-21: Follow-up to the CAN interface bring-up fix below: that fix only covers the interface being down at (re)connection time, not going down while the service is already running and connected -- confirmed on real hardware, the log filled with one `CAN bus write error: [Errno 100] Network is down` WARNING per dropped frame (e.g. once a second from the bridge's own self-announce timer alone). `Publisher._send_frame()` now catches this directly, since it's the only place that can (recv() never errors in this state -- no traffic arrives to trigger the read watch at all): first failure immediately retries `ensure_interface_up()`, further recovery attempts are rate-limited to once per 15s (a fixed interval, not exponential backoff -- discussed and deliberately chosen over reusing `RestartBackoff`, since bringing the interface up is cheap and idempotent, unlike the outer service-restart loop where each retry is expensive), and logging is edge-triggered (one WARNING when first noticed down, one INFO on recovery, DEBUG for repeated drops in between) instead of a WARNING per dropped frame.
- 2026-08-21: Fixed a real outage found after a Venus OS firmware update: the service itself stayed running (`svstat` showed it up) but published nothing, because `vecan1` came back administratively `DOWN` after the update and nothing brought it back up -- the interface bring-up (`ip link set vecan1 up type can bitrate 250000`) had always been treated as an external, one-time manual/system-level step (Phase 0's original design, `bus/socketcan.py`'s own docstring said so explicitly), and whatever had done that originally didn't run again on this boot. `SocketCanBus` now brings its own interface up if it isn't already (checked via the kernel's `IFF_UP` flag, never touching an interface that's already up), making this self-healing regardless of what caused the interface to be down. Also researched and documented (not previously written down) exactly how SetupHelper is supposed to survive a firmware update at all -- `/data/rcS.local` -> `reinstallMods` -> `/etc/venus/REINSTALL_PACKAGES` -> `PackageManager`'s own service rediscovers every package under `/data/` and reinstalls it -- useful for diagnosing the *next* "why isn't our service back after a firmware update" question, since this one turned out to be a CAN-interface problem, not a reinstall problem. See `dev-notes/VENUS_OS_CONSTRAINTS.md` and `ARCHITECTURE.md`.
- 2026-08-21: Re-leveled four log lines that fire once per D-Bus write (`switch_service.py`'s `_handle_state_write`/`_handle_dimming_write`) or once per command attempt (`publisher.py`'s queuing and send-attempt lines) from INFO down to DEBUG -- during a brightness-slider drag these could fire many times a second, which isn't useful at the default log level and burns through the rotating log file's history faster than necessary. The meaningful per-command outcome (`_finalize_command_attempt()`'s completed/did-not-complete, and every gate refusal) stays at INFO/WARNING. `log_level` in `config.json` (already existed, default `"INFO"`) is how to see the DEBUG detail again if needed -- no new config surface added. Log file size was already bounded (`RotatingFileHandler`, 10MB x 7 backups = 80MB max, since Phase 2) and unaffected by this change; the perceived "unreasonably large" growth was the noise burning through that cap faster, not unbounded growth.
- 2026-08-21: Added GUI panel grouping support for switch-kind devices, following up on the sort-order investigation below: `/SwitchableOutput/0/Settings/Group` is now registered (writeable, default `""`, matching `victronenergy/dbus-switch`'s reference pattern) so devices can be consolidated into one Cerbo GUI panel by giving them the same group name -- editable either from the Cerbo GUI's own per-output settings page or from `manage-devices` (new "Set GUI panel group" action, switch-kind devices only). Persisted via a new `group` field in `config.json` (`ConfigManager.get_device_group()`/`set_device_group()`, defaults to `""`/ungrouped, never `None`) rather than Venus's own local-settings mechanism, for consistency with how every other device setting in this project is stored. 281 tests passing.
- 2026-08-21: Fixed switch panel sort order in the Cerbo GUI (real-hardware observation: panels appeared in no discernible order). Root-caused against Victron's own `gui-v2` source (`src/device.cpp`, `src/basedevice.cpp`): panels sort alphabetically by device name, which falls back to `/ProductName` when `/CustomName` isn't set at the D-Bus service root -- `switch_service.py` only ever set `/ProductName="OneControl Switch"`, identical across every device, so every panel tied on the sort key and fell back to CAN-bus DEVICE_ID broadcast timing (effectively arbitrary) to break the tie. Fixed by registering a real root `/CustomName`, matching Victron's own reference driver (`dbus-switch.py`) and matching what `tank_service.py`/`motor_status_service.py` were already doing correctly -- this bug was specific to `switch_service.py`. Root `/CustomName` and the per-channel `Settings/CustomName`/`Name` paths are kept in sync regardless of which one is edited. Separately confirmed (same investigation) that panel *grouping* is unrelated to `/ProductName` matching -- it's driven by an explicit, currently-unset `Settings/Group` path (`gui-v2/src/iochannelgroupmodel.cpp`), already exposed as a real editable field in the Cerbo GUI's own per-output settings page; not added yet, pending a decision on whether/how to persist it.
- 2026-08-21: Fixed a real bug found during first real-hardware test of Phase 3 commands: dragging a dimmable light's brightness slider in the Cerbo GUI generated a flood of "a command is already in flight" refusals, since a real TEA handshake takes longer than the GUI generates write events during a drag -- meaning the light could settle on an early drag position rather than wherever the slider was actually released, not just log noise. Fixed by coalescing: a write that arrives while one's already in flight for that device is queued (overwriting any previous queued value, never accumulating a backlog) and re-attempted -- against a freshly re-evaluated command gate, not the stale decision from when it was queued -- the moment the in-flight attempt finishes, in `publisher.py`'s `_finalize_command_attempt()`. A real bus outage clears both the in-flight and queued state, so recovery never resumes a stale write. See `dev-notes/ARCHITECTURE.md`'s Command Flow section.
- 2026-08-20: `enable-device` renamed to `manage-devices` and extended with a "Manage existing devices" mode -- rename, toggle `expose`, toggle `commands_enabled`, and remove a device already in `config.json`, none of which were previously possible without hand-editing the file. The backend (`ConfigManager.update_friendly_name()`/`set_expose()`/`set_commands_enabled()`/`remove_device()`) already existed and was already unit tested; this was purely a CLI/UX gap. The rename was prompted by the tool outgrowing its original name once it did more than enable new devices. Folded into the existing top-level menu (a new `M) Manage existing devices` option) rather than a separate script or an extra top-level mode-choice step, so adding a new device -- still the common case -- has zero added friction. `device_class` remains uneditable everywhere in the tool, matching the existing "inferred, never asked" design. One behavior worth knowing: toggling `commands_enabled` takes effect live (the command safety gate reads config fresh from disk on every write attempt), but toggling `expose` off or removing a device does not retract it from D-Bus until the service restarts, since `publisher.py` only ever creates a device's D-Bus service and never tears one down in response to a config change -- same restart-required convention the add flow already had.
- 2026-08-20: Fixed a real resource leak in `publisher.py`, found during a post-implementation review the user asked for ("be resource-conscious"): none of the GLib timers/IO watch registered in `run()` (`_check_stale_services`, the Phase 3 command-timeout sweep, the address-claim window/backoff timers, the bridge self-announce timer) were ever removed on a crash-restart cycle -- GLib sources attach to the process-wide default main context, not to a particular loop object, so each in-process restart stacked a duplicate set of periodic timers on top of every previous one, compounding forever (extra CPU, extra log noise, and for the self-announce timer specifically, real duplicate CAN bus traffic). Fixed by tracking every source id (`Publisher._add_glib_source()`) and removing them all in `_cleanup()`. Found and fixed two related issues in the same pass: (1) none of `publisher.py`'s outbound `self.bus.send()` calls were exception-guarded, so a single transient CAN write error would crash the whole main loop and force an unnecessary full restart of every device's D-Bus presence -- wrapped in a new `_send_frame()` helper that logs and drops the one frame instead; (2) each D-Bus service's private `dbus.SystemBus(private=True)` connection was never explicitly closed on `service.close()` -- confirmed via dbus-python's own docs that `Connection.close()` exists and isn't implied by `__del__()`/garbage collection (`VeDbusService`'s internal objects hold reference cycles back to themselves that delay GC further) -- fixed in all three service classes (`tank_service.py`, `switch_service.py`, `motor_status_service.py`). All three bugs share the same trigger (a crash-restart cycle) and the same practical effect (accumulating leaked resources the longer a flaky bus/network stays flaky) -- not yet exercised on real hardware, but 275 tests still pass and every module still `py_compile`s clean.
- 2026-08-20: Phase 3 (safe commands) implemented, not yet rolled out to real hardware. Empirically determined the real CAN address-claim procedure from a live power-cycle capture (`samples/poweroutage_capture.log`) rather than hardcoding an address, after the user asked whether it could be figured out properly instead of guessed and captured it themselves -- `can_link/address_claim.py`. Found and corrected a real discrepancy in the dimmable-light COMMAND byte layout along the way: the community-documented format (`brightness 1-100`) didn't match a real on/off command capture at all; a targeted follow-up capture of an actual brightness-slider drag (`samples/dimming_capture.log`) resolved it completely -- brightness is a raw 0-255 scale (matching `DEVICE_STATUS`'s own scale), and a plain tap uses a separate simplified toggle command distinct from the granular set-brightness one. Added `can_link/command_sequencer.py` (async TEA-handshake-through-COMMAND state machine that re-verifies the command safety gate a second time immediately before sending COMMAND, not just when the attempt started) and `dbus_bridge/{command_mapping,command_gate}.py` (device_class -> CAN frame dispatch and the layered command-enable safety gate). `switch_service.py`'s `/SwitchableOutput/0/State` and `/Dimming` are now both writeable -- same always-reject-but-report UX as Phase 2's rejected writes, but now a real command is actually attempted in the background. `enable-device` gained an optional `commands_enabled` prompt, folded into its existing flow per explicit user request rather than kept as a separate action. 275 tests passing.
