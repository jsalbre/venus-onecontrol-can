# Changelog

All notable changes to this project are documented here, newest first. This file is append-only — do not revise past entries.

## Unreleased

- 2026-08-20: Fixed a deployment-process bug: an initial partial-file copy (`enable-device` alone, without the `dbus_bridge/device_mapping.py` functions it depends on) broke with an ImportError on the Cerbo. Corrected the deployment procedure to always do a full tarball sync (excluding `config.json`) followed by `setup install auto` -- confirmed by reading SetupHelper's `HelperResources/ServiceResources` directly that `installService()` already handles a clean `svc -t` restart itself when the service is already running, so no manual `svc -d`/`svc -u` is needed or wanted. Documented in README.md and `dev-notes/VENUS_OS_CONSTRAINTS.md`, including why `INSTALL_FILES`/`fileList` is a legitimate no-op for a self-contained package like this one. `enable-device` subsequently confirmed working end-to-end on the real Cerbo: added Tank Heater, Kitchen Island Light, and Kitchen Pendants Light, all with correctly auto-inferred device_class and zero device-instance collisions across what's now 4 tank + 4 switch services.

- 2026-08-20: Redeployed the device-instance collision fix -- confirmed on real hardware: the four tank services now register with four distinct instances (76, 86, 58, 87). Also confirmed the switch service's Phase 2 write-rejection behavior live: tapping the water pump switch in the Cerbo GUI correctly reverted to its previous state instead of showing a stale/incorrect "on"; toggling the pump from the physical OneControl panel updated the Venus GUI immediately. Added `enable-device`, an interactive CLI (UX borrowed from `govee-ble-venus-py/add-sensor.sh`) for adding a discovered device to `config.json` without hand-editing it. Per explicit user feedback, it never asks for `device_class` -- `device_mapping.infer_device_class()` derives it automatically from DEVICE_TYPE + FUNCTION_NAME, the same way a human reviewing `discovered_devices.json` would, and `build_addable_list()` filters the menu down to devices that are both supported and reliably identifiable (excluding `(PRODUCT_ID, instance)` fallback keys, which can't be tied to a single physical device). Verified end-to-end against the real `discovered_devices.json` produced by this deployment.
- 2026-08-20: First real deployment to the Cerbo succeeded (4 tank services + the water pump switch service registered on D-Bus; safety-gate write rejection confirmed working live in the log). Found and fixed a real bug in the process: device instance assignment (`stable_id_for(key, modulo=100)`) is evenly distributed but not collision-free, and two tank services (Grey Tank 1, Black Tank) landed on the identical instance (86) on first boot. Fixed with `device_mapping.assign_device_instance()` -- checks against every other already-assigned instance of the same kind, linearly probes to a free slot on collision, and persists the result to `config.json` (new `device_instance` field, `ConfigManager.get_device_instance()`/`set_device_instance()`/`get_instances_by_kind()`) so it never moves again once assigned. Regression-tested against the exact real colliding keys.
- 2026-08-20: Replaced `can_link/types.py`'s ~25-entry placeholder `FUNCTION_NAMES` table with the real, complete 446-entry table extracted from the decompiled LippertConnect Android app (values 0-445, no gaps, no duplicate keys). Device names are never transmitted over the CAN bus -- the app resolves the numeric FUNCTION_NAME code locally against this same table, and this project now does too, so friendly names match what the user's phone app actually shows (e.g. `38 -> "Kitchen Island Light"`, `122 -> "Scare Light"`). Also confirmed, independently of this project, that the `(FUNCTION_NAME, function_instance)` stable-key design matches Lippert's own gateway architecture (`DeviceInstanceManager.GetAvailableDeviceInstanceClaim` uses the same strategy internally) -- no design change, but real validation. Updated `config.example.json` to use exact vendor names. Reframed the 13-device `FUNCTION_NAME=0` stable-key collision (documented 2026-08-19) as known-empty/unconfigured Unity module ports per the user, not a gap needing investigation -- and identified the concrete PID 4/5 write mechanism that would be used to configure one of those ports in the future, if ever needed.
- 2026-08-19: Phase 2 (D-Bus publishing) implemented: `dbus_bridge/{config_manager,device_mapping,routing,backoff}.py` (pure, unit tested) and `dbus_bridge/{tank,switch,motor_status}_service.py` + `publisher.py` (require dbus/gi, Cerbo-only). Tanks use the documented `com.victronenergy.tank` service; lights/pump/water-heater use `com.victronenergy.switch` following the exact path structure confirmed from Victron's own `dbus-shelly` driver, read-only until Phase 3 (write attempts are rejected with a clear log message, not silently accepted); motor status uses a custom non-standard service with no writable state path at all. Exposure requires an explicit `expose: true` config entry AND a live device-class cross-check (`routing.route_device_id()`) -- both are fail-closed and unit tested, including the specific case of a motor mistakenly configured as a commandable device_class. Also added SetupHelper deployment packaging (`setup`, `services/onecontrol-can/`, `GUI_V1_NOT_REQUIRED`). Not yet run against real hardware -- next step is deploying to the Cerbo.
- 2026-08-19: Corrected an earlier overstated finding: CIRCUIT_ID (message type 1) traffic was flagged as "non-trivial" based only on how many devices sent it. Re-checked the actual payload content — all 1525 CIRCUIT_ID frames in the capture, from all 31 devices, are exactly `00000000`, matching the source research's "all-zero, unused" characterization. No investigation needed; Phase 1 is now fully closed except the deferred, low-priority PID battery voltage item.
- 2026-08-19: Tank sensor decoding confirmed by user against real known tank levels (fresh 66%, grey 66%/33%, black 33%). Phase 1 decoder validation is essentially complete — only PID battery voltage (deferred, low priority) and the CIRCUIT_ID traffic investigation remain open.
- 2026-08-19: Fixed `decode_tank_sensor` — `battery_level_pct=0xFF` is a "not supported" sentinel (like `measurement_quality_pct`), not a literal 255%. Found by re-examining the real capture: all 8 tank sensors on this coach reported exactly 255 regardless of otherwise-plausible fill levels (66%, 33%, etc.), consistent with wired sensors that have no battery to report.
- 2026-08-19: Documented (not fixed — no fix exists yet) a real stable-key collision: 13 of 31 devices discovered in the capture share an identical fallback key because they're unconfigured (FUNCTION_NAME=0) and also share PRODUCT_ID/instance. Tied to the new "System Configuration via CAN" TODO item.
- 2026-08-19: First real capture from this coach's OneControl bus (Cerbo wired in as the new bus end, interface `vecan1`). 1514 DEVICE_ID broadcasts decoded cleanly across 31 discovered devices, zero decode errors. TEA cipher confirmed exactly against 8 real seed/key pairs captured during light-control sessions. Relay/motor status decoder confirmed against a real water pump ON/OFF/ON cycle; dimmable light status decoder confirmed against two real light ON/OFF cycles; a third light (relay-driven, non-dimmable) also confirmed. Tank sensor status and PID battery voltage reads remain unvalidated (not exercised in this capture).
- Project scaffolding and documentation structure established.
- Protocol decoder library (`can_link/`) implemented per the cross-validated IDS-CAN protocol research (esphome-onecontrol, UnityX-canbus, manos/OneControl-RV-C-Protocol), covering CAN ID encode/decode, DEVICE_ID/DEVICE_STATUS decoding, PID reads, TEA-cipher session handshake, command frame builders, and the stable-key discovery/address-resolution table with bus-outage safety gating.
- Phase 0 raw capture tool (`candump_logger.py`) and Phase 1 replay/validation harness (`candump_replay.py`) implemented.
- Not yet validated against real hardware — the OneControl CAN bus is not wired to the Cerbo yet. All decode tables are sourced from other coaches' reverse-engineering and are unverified for this Unity X270 until Phase 0/1 acceptance criteria are met.
