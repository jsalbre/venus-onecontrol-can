## Future Phase — Device Reconfiguration via CAN (research substantially done 2026-08-21, write path not yet built)

Two real goals: (1) assign a name/function to a currently-unused Unity X270 input/output (e.g. the unused generator output), (2) fix a real problem -- the Kitchen Island lights sit on one of the X270's 4 dimming-capable outputs but don't dim in either the OneControl app or this project (any `Dimming` write under 100% snaps back to 100%), strongly suggesting that specific output is internally configured as a latch despite dimmable-capable hardware.

- [x] **PID write mechanics confirmed** (2026-08-21, decompiled LippertConnect source): PID writes reuse request code `0x11` (the same as reads), distinguished by payload length -- no new wire-level message type.
- [x] **Rename/reassign mechanism confirmed and corrected**: PID 4 (`IDS_CAN_FUNCTION_NAME`) / PID 5 (`IDS_CAN_FUNCTION_INSTANCE`) writes are real -- matches Lippert's own official `OneControl Configurator Guide` (CCD-0001830) `DEVICE NAME` section, shown used on a device literally labeled `UNKNOWN`. **Correction to the previous entry here:** these writes require the **DIAGNOSTIC session (SESSION_ID=2)**, not `REMOTE_CONTROL` (SESSION_ID=4) as originally guessed -- cross-validated numerically (decompiled `REMOTE_CONTROL` cypher converts to exactly `0xB16B00B5`, the same value already proven against 8 real handshakes).
- [x] **Dimmable-output problem re-scoped, not solved**: confirmed via the same official Configurator Guide that Lippert has no dimmable-to-relay conversion feature anywhere -- the only dimmer-specific setting exposed is `DEVICE SWITCH TYPE` (Toggle/Momentary, a physical wall-switch behavior, not the output's own dimming capability). `LOAD_TYPE` (PID 451) looked like a real, specific candidate for what's clamping this output -- **ruled out**, see below.
- [x] **No real validating capture is possible** -- confirmed with the user: the phone app can't reconfigure at all (UI-gated, not protocol-gated -- the reconfiguration code exists in the decompiled app, just has no UI entry point), only the physical touchscreen can, which this installation doesn't have.
- [x] **Read-only probe tool built** (2026-08-21, `src/tools/pid_probe.py` + `can_link/pid_client.py`'s new `PID_GET_PROPERTIES` (0x12) support): queries a real device's raw PID values and whether a PID is reported as writable at all, with zero risk -- no session opened, no write, ever. See `ARCHITECTURE.md`'s "PID Reconfiguration" design decision.
- [x] **First real probe run (2026-08-21) disproved the `DEVICE_TYPE`(183)/`LOAD_TYPE`(451) hypothesis**: probed against Kitchen Island Light (misbehaving), Kitchen Pendants Light (working), and Fresh Tank (a deliberate cross-check, independently known to have a different real `DeviceType`) -- all three returned byte-identical replies for both PIDs. Decoding the reply's trailing byte against the decompiled `RESPONSE` enum confirmed why: it's `UNKNOWN_ID` (4) every time. Neither PID is recognized by this hardware family -- the decompiled catalog they came from likely covers a different Lippert product line. Also caught and fixed a real bug in `pid_probe.py` itself in the process (it printed the *requested* PID, not the one the device actually echoed, masking this).
- [x] **`PID_READ_LIST` (request code `0x10`) added** (2026-08-21, `pid_probe.py --list-pids`): enumerates every PID a specific real device actually supports, discovered directly instead of guessed from a possibly-mismatched catalog. Read-only, no session, same safety profile as the rest of the probe tool. 295 tests passing.
- [x] **Root cause found and confirmed on real hardware (2026-08-21):** `--list-pids` against Kitchen Island Light and Kitchen Pendants Light returned an identical 97-PID supported set on both -- the difference isn't which PIDs are supported, it's a value within that set. Cross-referencing all 97 against the full named PID catalog in the decompiled source found **PID 161 = `SIMULATE_ON_OFF_STYLE_LIGHT`** (DIAGNOSTIC-gated, writable on both devices) -- reads `1` on Kitchen Island Light (misbehaving), `0` on Kitchen Pendants Light (working). Also incidentally confirmed `parse_pid_reply()`'s previously-unvalidated success-reply shape is correct (real PID 161 reply decodes exactly as already implemented). See `ARCHITECTURE.md`'s "PID Reconfiguration" design decision and `dev-notes/ARCHITECTURE.md`'s `PID_READ_WRITE` section.
- [x] **Write path built and confirmed fixed on real hardware (2026-08-21):** generalized `session.py` for an arbitrary SESSION_ID/cypher, added `pid_client.build_pid_write_request()`, and built `src/tools/pid_write.py` (manual, `--confirm`-gated, never wired into any production path). First write attempt (1-byte value) was rejected `BAD_REQUEST` -- resolved by using the PID's full declared `Formatter` width (6 bytes, `UINT48`) instead of a read's truncated width. Writing PID 161 = 0 on Kitchen Island Light succeeded (`RESPONSE.SUCCESS`, read-back confirmed) and the user confirmed the light dims correctly now, with the OneControl phone app also showing it as a dimmer after a restart. DIAGNOSTIC session (SESSION_ID=2) is now real-hardware-confirmed, not just decompiled-only. 306 tests passing. See `ARCHITECTURE.md`/`dev-notes/ARCHITECTURE.md` for the full writeup.
- [ ] **Deferred, not started:** production integration -- `manage-devices` UI for reconfiguration, PID 4/5 rename/reassign support (mechanism confirmed, not yet built), any automatic/production write path in `publisher.py`. `pid_write.py` remains a manual, one-shot diagnostic tool for now; this is a separate planning pass if/when a permanent feature is wanted.
- **On the FUNCTION_NAME=0 collision (13 of 31 devices in the 2026-08-19 capture sharing an identical fallback `(PRODUCT_ID=232, instance=42)` stable key):** per the user, these are understood to just be unused/unconfigured physical input connections on the Unity module itself (empty ports with nothing wired to them) — not mystery devices needing investigation.
